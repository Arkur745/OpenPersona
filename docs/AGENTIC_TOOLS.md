# Agentic tool use (LangGraph ReAct agent) — design note

> **Status (2026-10-19): implemented**, per persona rather than as one
> global agent. See `docs/ARCHITECTURE.md`'s "Agentic personas" section
> for what was built. Where the build differs from this note:
> - **Per-persona tools.** Each persona lists its own `tools:`, and only
>   personas with tools go through the agent.
> - **No keyword pre-filter (§1).** The streaming bug that motivated it
>   didn't reproduce with qwen2.5:7b-instruct on LangGraph 1.2 / Ollama
>   0.24 (measured), so the model itself decides on each turn whether to
>   call a tool.
> - **Filler timing (§4).** The filler is spoken when the model actually
>   calls a tool (`ToolStarted`), not on a heuristic guess. No new
>   voice-turn state was needed: the "waiting on a tool" period stays
>   inside "speaking response", and the sentence source wakes on barge-in
>   while waiting.
> - **First tools are offline** (notes, reminders, calculator, date/time,
>   memory search). Web search uses `ddgs` rather than Tavily, needs no
>   API key, and, like weather (Open-Meteo), is off unless
>   `agent.options.allow_network: true`.
>
> The rest of this note is the original proposal, kept for its reasoning.

Same gate every prior design note in this project got: this is a design
note only. No adapter code, no new interface, no `Orchestrator` changes.
Everything below is grounded in reading `Orchestrator.handle_text_turn`/
`handle_voice_turn`, `PromptBuilder.build()`, and `OllamaLLM
.generate_stream()` as they actually exist today (not assumed or
remembered from an earlier pass), plus current LangGraph/LangChain
documentation and package metadata (not training-data recollection —
verified live, cited inline).

## 1. Where this plugs into `Orchestrator`, concretely

### The exact swap points, traced from real code

**`handle_text_turn`** (`companion/core/orchestrator/orchestrator.py:140-179`):
after `PromptBuilder.build()` produces `built: BuiltPrompt`, the reply is
generated by exactly one expression:

```python
reply = "".join(
    [token async for token in self.generate_reply(built.prompt, built.context)]
)
```

This is the swap point. Nothing before it (`memory.query`,
`_dedup_retrieved_memory`, `PromptBuilder.build()`) or after it
(`_write_turn_safely` ×2, `return reply`) needs to change shape — `reply`
just needs to end up as a plain `str` either way, exactly as it does
today.

**`handle_voice_turn`** (same file, `343-553`): the analogous point is

```python
async for sentence in self._sentences_from_llm(built.prompt, built.context):
    response_sentences.append(sentence)
    ...
    async for audio_chunk in self.tts.synthesize_stream(sentence):
        ...
        yield audio_chunk
```

`_sentences_from_llm` (`264-281`) is what bridges token streaming to
TTS's sentence granularity via `_pop_complete_sentence`. This is the real
complication voice mode adds that text mode doesn't have — see section 4.

### Always-agentic vs. conditional — recommendation: **conditional**, gated by a cheap heuristic, not a second LLM call

This is not a coin flip between two equally-reasonable options; one real,
documented constraint decides it. LangGraph's `create_react_agent`
supports token-level streaming via `stream_mode="messages"` in general,
but **there is an open, reproducible bug where this does not work when
tools are bound to the model**
([langchain-ai/langgraph#5249](https://github.com/langchain-ai/langgraph/issues/5249)).
Binding tools to every turn — even turns that end up not using one — is
exactly the "always-agentic" design, and it would mean *every* reply in
this project, including plain "how's your day" chit-chat, loses reliable
token-level streaming. That's not a minor regression: `_sentences_from_llm`
and voice mode's whole first-sentence-starts-TTS-early design exist
*because* token streaming is what lets a voice response start sounding
quickly. Trading that away on every turn, for a capability (search) most
turns will never use, is a bad default — consistent with how every other
optional capability in this project has shipped (MemArk: a second,
opt-in `MemoryStore` backend, not a replacement of Chroma; the Streamlit
UI: additive, not a replacement of the CLI; push-to-talk voice in
Streamlit: an added mode, not a change to the existing text path).

**Recommendation**: a fast, local, zero-LLM-call heuristic prefilter
decides whether a given `user_message` plausibly needs a tool *before*
either path runs. Concretely: keyword/pattern matching against the
message text (time-sensitive phrasing — "today", "right now", "latest",
"current" — explicit lookup phrasing — "search for", "look up", "what's
the weather", "who won" — question words combined with proper nouns the
model likely wasn't trained on recently). If it matches, route through
the LangGraph agent path (section 2); if not, take the existing direct
`generate_reply`/`_sentences_from_llm` path completely unchanged.

Why a heuristic and not a second small LLM call to classify intent
first: a classification call still costs a real round-trip on *every*
turn (defeating the purpose — the whole reason to avoid always-binding
tools was to keep the common case cheap and streaming), while a keyword
heuristic costs nothing measurable. The honest cost is recall, not
latency: a heuristic will have real false negatives (a legitimately
tool-needing question phrased in a way the patterns don't catch) — for a
companion app, a wrong-but-plausible answer from the model's own
knowledge on a missed edge case is an acceptable trade against paying a
latency/streaming cost on every single turn to catch it. This is a
recall-favoring, not precision-favoring, design choice, stated plainly
rather than glossed over. Tuning that pattern list is explicitly out of
scope here — see section 6.

### Where the decision and the agent object live

Not inside `PromptBuilder` — it's documented (`docs/PROMPT_BUILDER.md`,
this file's own docstring) as a pure assembly function with no
decision-making, and adding "does this need a tool" logic there would
break that single-responsibility boundary the same way adding a
`MemoryStore` call to it was explicitly rejected for in that note.

Recommendation: a plain injected collaborator on `Orchestrator`, new
optional constructor parameter, default `None` — same pattern already
used for `handle_voice_turn`'s `on_playback_interrupt`/
`wait_for_playback_drained` (optional, defaults preserve every existing
caller/test unmodified). Not a new one of the five abstract interfaces
in `core/interfaces/` — this doesn't touch STT/TTS/LLM/VAD/MemoryStore's
contracts at all, and there's only one real implementation in view
(LangGraph), so promoting this to a formal ABC now would be the same
mistake `VoiceActivityDetector`'s `frame_bytes` gap explicitly avoided
repeating (`docs/ARCHITECTURE.md`'s "VAD" section: don't add abstract
surface on the strength of one implementation). Concretely: something
like `Orchestrator(..., agent: AgenticToolRunner | None = None)` where
`AgenticToolRunner` is a small, project-owned wrapper (not a raw
LangGraph object passed in directly) exposing roughly `async def
maybe_run(message: str, built: BuiltPrompt) -> str | None` — returns
`None` if its own heuristic decides no tool is needed (falls through to
the existing direct path), or the final answer text if it ran the agent
loop. Keeping the heuristic *inside* this wrapper, not inside
`Orchestrator` itself, keeps `Orchestrator` from growing tool-specific
logic directly — consistent with it staying "backend-agnostic," now
extended to mean "agentic-tooling-agnostic" too.

## 2. The message-format boundary

### The real shape on both sides, confirmed against source

`OllamaLLM.generate_stream` (`companion/backends/llm/ollama_local.py:110-119`)
builds Ollama's chat message list as:

```python
messages = [{"role": "system", "content": prompt}]
messages.extend({"role": turn.role, "content": turn.text} for turn in context)
```

i.e. `Turn.role` values ("user"/"assistant") map directly onto chat
message roles today. `PromptBuilder.build()` (`prompt_builder.py:74-112`)
only ever appends `Turn(role="user", ...)` for the live message, and
every `Turn` written to `MemoryStore` (`Orchestrator._write_turn_safely`
call sites, `orchestrator.py:171-177`, `485-488`, `542-547`) is
hardcoded `role="user"` or `role="assistant"` — never `"system"`.
`context` in practice is exhaustively user/assistant turns, even though
`Turn.role`'s type (`Literal["user", "assistant", "system"]`) allows a
third value nothing in this codebase currently produces.

LangGraph's `create_react_agent` (`langgraph.prebuilt`, package
`langgraph-prebuilt`) is invoked as `agent.ainvoke({"messages": [...]})`
and returns `{"messages": [...]}` — the full accumulated message list,
last entry the final `AIMessage` once no more `tool_calls` are pending.
Input messages can be plain `{"role": ..., "content": ...}` dicts *or*
`langchain_core.messages` objects
(`HumanMessage`/`AIMessage`/`SystemMessage`/`ToolMessage`) — verified
directly against LangChain's reference docs, not assumed. Explicit
message objects are the better choice here: same clarity the project
already gets from `Turn` being a real dataclass rather than a bare dict,
and it makes the role-mapping's exhaustiveness (see above) a type-level
fact instead of a string convention.

### The two adapter functions this needs

```python
def _built_prompt_to_messages(built: BuiltPrompt) -> list[BaseMessage]:
    messages: list[BaseMessage] = [SystemMessage(content=built.prompt)]
    for turn in built.context:
        if turn.role == "user":
            messages.append(HumanMessage(content=turn.text))
        elif turn.role == "assistant":
            messages.append(AIMessage(content=turn.text))
        else:
            # Never actually produced today (see above) — fail loudly
            # rather than silently mis-mapping a role nothing currently
            # creates, matching this project's established posture.
            raise ValueError(f"unexpected Turn.role in context: {turn.role!r}")
    return messages
```

```python
def _agent_result_to_text(result: dict) -> str:
    final = result["messages"][-1]
    # A text-only Ollama chat model always returns a plain string here;
    # some providers can return a list of content blocks (multi-modal)
    # — not a case this project's LLM layer has ever needed to handle
    # (OllamaLLM's own content is always str), so this isn't a new
    # assumption, just carrying the existing one forward explicitly.
    return final.content
```

With these two functions, the integration at both swap points from
section 1 is genuinely minimal: `handle_text_turn`'s `reply = "".join(...)`
expression becomes (conceptually) `reply = agent_text or "".join(...)`
where `agent_text` is `None` when the heuristic declined the tool path.
Nothing about `handle_text_turn`'s surrounding structure — the memory
query/dedup before, the two `_write_turn_safely` calls after — needs to
change at all.

`handle_voice_turn` needs one more piece: since the agent path isn't
reliably streamable (section 1), its full final text has to be
re-chunked into sentences for TTS the same way streamed tokens are
today. This reuses `_pop_complete_sentence` directly — feed the whole
final string through it in a loop (or just `str.split` on the same
sentence-boundary regex once, since there's no "more might arrive"
uncertainty for a already-complete string) — so `handle_voice_turn`'s
downstream `async for sentence in ...: yield audio chunks` loop needs
*zero* changes; it only ever sees a stream of complete sentences,
regardless of whether they arrived token-by-token or all at once.

## 3. What gets persisted to memory, and what doesn't

Confirmed directly: today, exactly two `Turn`s are written per exchange
— the user's message and the model's full final reply, both as plain
strings, nothing else (`orchestrator.py:171-177` for text mode; `485-488`
+ `542-547` for voice mode, where the assistant `Turn` is `" "
.join(response_sentences)` — every sentence that was actually spoken,
concatenated).

**For a tool-augmented exchange, `MemoryStore.write()` should receive
exactly the same shape**: the user's original question, and the agent's
final natural-language answer — never the intermediate `AIMessage` that
carries `tool_calls` (its `.content` is typically empty or a
tool-call-only placeholder, not real prose), never the `ToolMessage`
(raw search-API output — noisy, not something a companion "said"), and,
in voice mode, never the filler phrase either (see section 4 — it's a
UI/UX affordance, not something worth recalling later, e.g. "I said
'let me check on that'" is not a fact about the user or the
conversation).

`_agent_result_to_text` (section 2) already isolates the right thing —
it's exactly what should end up as the assistant `Turn`'s `text`.

**One real implementation trap worth naming now, not discovering
later**: `handle_voice_turn`'s current accumulation pattern —
`response_sentences.append(sentence)` for *every* sentence yielded from
`_sentences_from_llm`, later flat-joined and written as one `Turn` — is
exactly wrong for a filler-augmented turn if reused unmodified, because
the filler sentence would get appended to the same list and end up
inside the persisted assistant `Turn`. This needs the implementation to
track "filler sentence(s)" separately from "real answer sentences" and
join only the latter for the `Turn` that gets written — a small but
easy-to-miss divergence from today's flat accumulation, exactly the kind
of gap this project's own history (the `_pump_mic` queue-reuse bug, the
Streamlit clear-button `KeyError`) shows gets caught by real testing if
not caught here first.

**Confirmed, not assumed: no changes needed to `_dedup_retrieved_memory`
or `PromptBuilder`.** Both operate purely on `Turn` objects by value
(role/text/timestamp) — `_dedup_retrieved_memory` drops anything already
in `recent_turns` by equality; `PromptBuilder.build()` renders whatever
`Turn`s it's given, with no awareness of how they were produced. As long
as what reaches `write()` (and therefore what a later `query()` can
return) is an ordinary, well-formed `Turn` — which the design above
guarantees — nothing downstream ever needs to know a tool was involved
in producing it. This is a genuine confirmation, not a hopeful one: both
functions were re-read for this note specifically to check this claim,
not carried over from memory of an earlier pass.

## 4. Voice-mode latency and filler response

### Text mode first, briefly, to confirm the scope split is real

`handle_text_turn` is request/response with no timing contract beyond
"return when done" — there's no VAD, no barge-in, no audio device, no
sub-800ms anything. A tool call taking an extra 1-3 real seconds just
means the caller's `await handle_text_turn(...)` takes longer; nothing
about `_dedup_retrieved_memory`, `PromptBuilder`, or the write-after
logic needs any latency-aware machinery. **Confirmed explicitly: none of
what follows in this section applies to text mode.** The only
text-mode-relevant UX question — showing a "searching..." indicator
while waiting — is a UI-layer concern (e.g. `companion/ui/streamlit_app.py`),
not an `Orchestrator` one, and out of scope for this note.

### Voice mode: the real mechanism, not a deferral

**Yes — the persona should say something before the tool resolves, not
sit in silence.** Silence for 1-3+ seconds after the user finishes
speaking reads as broken, not thoughtful, in a voice interface tuned
for sub-second response starts everywhere else.

**Concrete proposed mechanism:**

1. The same heuristic from section 1 decides a tool is likely needed.
2. The tool-capable agent invocation (`agent.maybe_run(...)`, section 1)
   is started immediately as its own `asyncio.Task` — **not awaited
   yet**. This is the load-bearing detail: kicking it off *before*
   speaking the filler means the real network/tool latency overlaps with
   filler playback instead of stacking after it. Total added latency
   becomes `max(filler duration, tool duration) + final-answer time`,
   not `filler duration + tool duration + final-answer time`.
3. Concurrently, one short, **fixed, non-LLM-generated** filler sentence
   is spoken through the *existing* TTS pipeline — `self.tts
   .synthesize_stream(filler_text)`, exactly like any other sentence.
   Non-LLM-generated is deliberate: generating the filler with the LLM
   would add its own latency before the filler could even start, which
   defeats the point. Source of the phrase: a small, persona-flavored
   set (e.g. a new optional `filler_phrases: list[str]` persona field,
   falling back to a small generic set — "Let me check on that.", "One
   sec, let me look that up." — for personas that don't define their
   own). This needs a `companion/core/persona_loader/` schema update
   (its `_KNOWN_FIELDS` check currently rejects unrecognized keys —
   confirmed directly against `persona_loader.py`) — flagged, not
   designed here; see section 6.
4. **No new voice-turn state for the filler itself** — it's just another
   sentence inside the existing "speaking response" state
   (`docs/ARCHITECTURE.md`'s state diagram). The existing barge-in
   watcher (`watch_for_barge_in`, `orchestrator.py:494-512`) already
   covers *any* spoken sentence uniformly; no special-casing needed for
   "this one's a filler."
5. If the tool task resolves before the filler finishes playing: let the
   filler finish naturally (it's short — on the order of a second), then
   continue straight into the real answer. No self-interruption
   mid-filler; the seam should be invisible in the common case where
   the tool is fast.
6. If the tool task is still running after the filler finishes: there is
   a real, honest silent gap here — **not fully masked by this design**,
   just reduced by however long the filler bought. This is the piece
   most worth validating once built, not asserting confidently now: how
   long real search-tool round trips actually take vs. how long a
   natural-sounding filler phrase takes to speak. If that gap turns out
   to be routinely long, a second, later filler ("still looking...")
   is a plausible follow-up, deliberately not designed here.
7. **Bound the tool call with a timeout, voice-mode-specific.** Text
   mode can afford to just wait; voice mode can't leave the user hanging
   indefinitely. On timeout: fall back to the model answering from its
   own knowledge with an honest caveat ("I couldn't check that right
   now, but...") rather than hanging the whole turn. The exact timeout
   value is a tuning question, not a design one — flagged, not set here.
8. **Interruptibility is uniform, not a special case — but barge-in
   during the filler has one real consequence needing explicit
   handling**: if the user barges in while the filler is still playing
   (or during the silent wait after it), `watch_for_barge_in` already
   calls `self.stop_speaking()`/`on_playback_interrupt()` exactly as it
   does today. The new requirement: the in-flight tool-call `asyncio
   .Task` from step 2 must also be cancelled at that point — otherwise
   it keeps running (wasting an API call/quota) and could resolve after
   the user has already moved on to a new utterance, with nowhere
   correct left to put its result. Combined with section 3: if barge-in
   happens before any real answer content exists yet (mid-filler, or
   during the wait), there is no real assistant text to write to memory
   at all — consistent with, not a special case of, today's rule that
   an interrupted response still writes "whatever text was actually
   generated" (here: none).

### Does this need a new voice-turn state? Yes, probably one — flagged, not designed

The filler itself, per point 4 above, fits cleanly inside the existing
"speaking response" state. **The gap does not**: the period after the
filler finishes but before the tool result (and therefore the real
answer) is ready is neither "listening" (not accepting a new
utterance-start), nor "speaking" (no audio playing), nor today's
"processing" (which currently has no observable duration or user-facing
state at all — it's the instant between VAD end-of-utterance and the
first sentence being ready). Naming and correctly wiring that state —
including exactly how it interacts with the barge-in watcher, and
whether `_pump_mic`'s single-consumer queue design (section-referenced:
`docs/ARCHITECTURE.md`'s "A real concurrency bug found while
implementing this" and "A real deadlock found via the first real,
continuous mic round trip" sections) needs any adjustment for a longer,
variable-duration wait — is real design work this note deliberately
does not do. Given this project's actual history of concurrency bugs
specifically in this state machine (the mic-ended-signal deadlock, the
playback-drain barge-in gap, both found by real execution, not review),
a new state here gets its own follow-up note before implementation, not
a paragraph tacked onto this one.

## 5. Dependency footprint

Verified against live PyPI package metadata (`requires_dist`), not
assumed from general knowledge of these libraries:

| Package | Declared runtime deps | Notes |
|---|---|---|
| `langgraph` | `langchain-core`, `langgraph-checkpoint`, `langgraph-prebuilt`, `langgraph-sdk`, `pydantic>=2.7.4`, `xxhash` | No torch, no heavy ML framework. |
| `langchain-ollama` | `langchain-core`, `ollama<1.0.0,>=0.6.1` | `ollama` is **already this project's own dependency** (`pyproject.toml`'s `llm-ollama`/`dev` extras pin `ollama>=0.3`) — no new package, and no version conflict (existing floor is looser). |
| `tavily-python` (the "at minimum" search tool named in scope) | `requests`, `tiktoken`, `httpx` | `httpx` is **already a dependency** (`llm-ollama`'s own extra — `ollama_local.py` imports it directly). Only genuinely new transitive package: `tiktoken` (a Rust-backed tokenizer, moderate weight, no torch). |

**Conclusion: this doesn't conflict with the local-first principle at
the dependency level.** Nothing here pulls in torch or a heavy ML
runtime — a real, verified relief given how much this project has
already gone out of its way to avoid exactly that (Chroma's ONNX
default over MemArk's sentence-transformers, MemArk's own adapter reusing
Chroma's embedder rather than pulling in `sentence-transformers`).

**Two real caveats, not dependency-weight ones:**

1. **Tavily itself is a cloud API, not a local one.** Unlike everything
   else this project runs, a tool-augmented turn that actually calls
   Tavily makes a real outbound network request to a third-party
   service. The LLM/tool-*decision* stays fully local (Ollama); only the
   *search execution* leaves the machine. This should be disclosed and
   opt-in the same way MemArk's experimental tradeoffs are — a config
   flag the user turns on knowingly, not a default-on behavior of a
   project whose whole pitch is local-first.
2. **Tool calling needs a tool-calling-capable model — not every Ollama
   model qualifies, including this project's own currently-configured
   one.** `ChatOllama.bind_tools()` only works with models actually
   fine-tuned/templated for tool calling. `qwen2.5`-family models
   (this project used `qwen2.5-coder:7b` earlier this session) are
   documented as tool-calling-capable; `dolphin-llama3:8b` (this
   project's *current* `config.yaml` selection, switched to later in
   this same session) is an uncensored general fine-tune of Llama 3, not
   a tool-calling one. Concretely: this feature would not work correctly
   against this project's own current default LLM choice without also
   switching models — a real, user-facing constraint worth stating
   plainly now rather than discovering it as a confusing runtime failure
   later.

## 6. Scope boundary, stated explicitly

This note designs the tool-calling loop and its `Orchestrator`
integration point only. It does **not** design:

- The actual `Tool` interface/adapter for any individual tool (Tavily
  specifically) — a separate, smaller note once this one is approved.
- Any new voice-mode state machine state(s) — flagged in section 4 as
  needing its own follow-up note, deliberately not designed here.
- Which specific tools ship first, or in what order.
- The heuristic prefilter's exact keyword/pattern list or tuning
  (section 1) — the *mechanism* (heuristic, not a second LLM call) is
  recommended and justified here; the specific patterns are an
  implementation/tuning detail.
- The `filler_phrases` persona-schema field's exact shape or the
  `persona_loader.py` change it needs (section 4) — flagged as required,
  not specified.
- Any config schema for enabling this feature or storing a Tavily API
  key — flagged as needed (a new top-level `tools:` config block,
  analogous to how `memory:`/`llm:` already work), not designed.

   either switch the default to a tool-calling-capable model or document
   the requirement plainly wherever this feature is configured (section
   5's second caveat).
